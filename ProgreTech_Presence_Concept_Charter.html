01 / Vision and problem statement

Turn otherwise invisible CLI agent activity into an ambient, useful representation of a running AI system. The interface should offer friendly identity and context without creating another autonomous execution layer or hiding which tool owns an action.

Primary users: AI developers, local-agent operators, tinkerers, and workstation owners managing several independent assistants.

02 / Goals and non-goals

  • Present a reactive avatar on the desktop, not just in a browser tab.
  • Show selected session, provider, task state, and approval needs.
  • Offer a companion application for providers, sessions, visual presets, and privacy settings.
  • Keep Open WebUI compatible with standard models and independent deployments.
  • Non-goal: intercepting every CLI process with root privileges or guaranteeing visibility into tools that expose no structured events.

Subsystem responsibilities

  • Wallpaper renderer: visuals, transitions, reduced-motion and frame budgets. No filesystem or shell privileges.
  • Presence daemon: tracks sessions, normalizes events, broadcasts state, persists local settings.
  • Integration adapters: explicitly supported sessions, status, streaming output, tool phases, completion and error events.
  • Open WebUI: chat, model/provider management, retrieval features. Keep native agent session control separate unless bridged.
  • Native host: tray/app indicator where supported, autostart, D-Bus, display management and lock-screen privacy.

Ubuntu implementation decision

Preferred: GTK4 + WebKitGTK/Wayland-aware native host for rendering HTML-based avatars, plus a PWA control center. On GNOME Wayland, a true animated background requires a tested shell extension or compatible desktop-layer solution; an ordinary always-below window is not guaranteed to behave like wallpaper.

Fallback: native desktop window/display mode using a compositor-supported layer mechanism; ship as an overlay mode first if the GNOME integration is unstable. Separate renderer and daemon to avoid impacting AI inference when animation fails.

05 / Canonical agent event protocol

State machine: disconnected → idle → listening → thinking → streaming → tool_running → approval_required → complete / error → idle. State changes originate from adapter events, never from guessed GPU usage. Collapse duplicate events, handle retries, and use heartbeats with timeout-to-unknown.

{
"schema_version": "1.0",
"session_id": "codex:local:session-123",
"provider": "codex",
"timestamp": "2026-10-18T18:00:00Z",
"event": "tool.started",
"state": "tool_running",
"task_label": "Updating project files",
"tool": {"type": "filesystem.write"},
"requires_approval": false
}

Animation/event mapping

  • Idle: slow breathing, subdued halo.
  • Listening: directional sound ripple, optional mic indicator.
  • Thinking: faster light-particle flow, oscillating bands.
  • Streaming: moving data strands tied to response chunks, not fabricated thoughts.
  • Tool execution: amber pathways and clearly labeled current tool.
  • Approval: deliberate amber pause and a notification requiring user action.
  • Complete: brief green pulse, fades to idle.
  • Error: restrained red pulse, actionable summary in control center.

Support reduced-motion and static modes as first-class settings.

07 / Security, reliability and resource budgets

Security requirements

  • Bind control API to loopback by default; authenticate browser and WebSocket clients.
  • Keep credentials in system keyring or restricted user files; never expose keys or prompts in wallpaper text.
  • No sudo, shell execution, arbitrary desktop capture, microphone, or file writes by default.
  • Use narrow allowlists, explicit approval prompts and agent-native permission enforcement.
  • Hide private content on lock-screen, screen-sharing and presentation modes.
  • Require explicit consent before enabling remote LAN, Tailscale or Cloudflare access.

Reliability and performance targets

  • Cold-start presence daemon after user login, without blocking desktop startup.
  • Target 30–60 FPS with GPU acceleration and tunable quality; no busy-loop when hidden.
  • Idle target under 3% aggregate CPU and under 500 MB renderer memory, to be measured on Rend.
  • Automatic reconnection with bounded exponential backoff; no duplicate commands after reconnect.
  • Fallback to static avatar on compositor/GPU error without breaking Codex or Ollama.
  • Collect telemetry locally only, opt-in export for debugging.

08 / Acceptance gates

  • A1: Wallpaper or desktop-layer fallback survives GNOME login/logout, workspace switching and multiple monitors.
  • A2: A managed Ollama/OpenCode task makes the avatar visibly change state in under 500 ms locally (target).
  • A3: Agent disconnects, process crashes and stale sessions are accurately labeled; never claim idle or success from missing data.
  • A4: Native approval is required for all sensitive actions and cannot be bypassed through the visualization.
  • A5: Control center can select agents, avatar themes, motion quality and privacy mode and retains settings across reboot.
  • A6: Open WebUI remains fully usable independently if the wallpaper service is stopped.

09 / ProgreTech Rend delivery method

Deliver one versioned Ubuntu ZIP bundle at a time, installing into a dedicated user directory and preserving existing agent configurations. Each bundle makes a specific targeted change before testing, prints its intended actions before changes, and finishes with machine-readable logs and human-readable results. Installer launcher follows the preferred flow: clear → unzip → run shell installer → clean extracted artifacts → leave output visible. Updates to project tracking record delivered outcomes only.

Suggested package boundaries: presence-daemon, presence-wallpaper, presence-control, presence-adapters, presence-installer. Keep independent versioning for the resident service and avatar assets.

10 / Open documentation and dependencies

Validated reference surfaces (October 2026): Open WebUI official docs · OpenAI-compatible provider protocol · OpenCode server API · OpenCode SDK. Verify Claude Code, Codex, and OpenClaw current integration APIs before implementation; CLI internals and hook schemas can change.

Design limitation: this concept does not claim to attach to arbitrary pre-existing terminal sessions; process introspection, stdout interception, and privileged monitoring are intentionally out of MVP scope.
